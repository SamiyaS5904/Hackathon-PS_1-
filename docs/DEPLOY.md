# Deploying Timetabl.ai

Three pieces, one database:

| Piece | Where | Address you get |
|---|---|---|
| Web app (`frontend/`) | Vercel | `https://<name>.vercel.app` |
| Backend API (`backend/`) | Render | `https://timetabl-backend.onrender.com` |
| Assistant (`chatbot/`) | Render | `https://timetabl-assistant.onrender.com` |
| Database | Supabase (already set up) | — |

Secrets are typed into each dashboard. They never go in the repository or in chat.

## 0. Before you start (5 minutes)

1. **Supabase region**: Supabase → Project Settings → General → *Region* (e.g. Mumbai `ap-south-1`).
   Render has no Mumbai region; pick the nearest: **Singapore** for India/Asia, Frankfurt for Europe,
   Oregon / Ohio for the US. Same continent = a few ms per query; across the world = 200+ ms.
   If the Supabase project is far from your users, it is worth creating a new Supabase project in
   Mumbai before the demo (the app creates its tables and the demo college by itself).
2. **Session pooler URL** (Render only speaks IPv4): Supabase → **Connect** → *Connection string* →
   Method **Session pooler** → copy. It contains `pooler.supabase.com`. Put your database password in
   place of `[YOUR-PASSWORD]`.

## 1. Backend and assistant on Render

1. Sign in at render.com with GitHub and allow access to the `Hackathon-PS_1-` repository.
2. **New → Blueprint** → choose the repository. Render reads `render.yaml` and shows two services.
   Change `region` in `render.yaml` first if Singapore is not nearest to your Supabase region.
3. Fill in the values it asks for:

   | Service | Setting | Value |
   |---|---|---|
   | timetabl-backend | `DATABASE_URL` | the Session pooler URL from step 0 |
   | timetabl-backend | `CORS_ORIGINS`, `FRONTEND_URL` | leave `http://localhost:3000` for now; set the Vercel URL in step 3 |
   | timetabl-assistant | `ANTHROPIC_API_KEY` | your Claude API key |
   | timetabl-assistant | `BACKEND_URL` | `https://timetabl-backend.onrender.com` |
   | timetabl-assistant | `CORS_ORIGINS` | same as the backend |

   `APP_SECRET` is generated by Render automatically.
4. **Apply**. The first build takes about 5 minutes. Check:
   `https://timetabl-backend.onrender.com/api/health` → `{"ok":true}` and
   `https://timetabl-assistant.onrender.com/health` → `"assistant_configured":true`.

## 2. Web app on Vercel

1. Sign in at vercel.com with GitHub → **Add New → Project** → import the repository.
2. **Root Directory**: `frontend` (Framework: Next.js is detected).
3. **Environment Variables**:
   - `NEXT_PUBLIC_BACKEND_URL` = `https://timetabl-backend.onrender.com`
   - `NEXT_PUBLIC_CHATBOT_URL` = `https://timetabl-assistant.onrender.com`
4. **Deploy**. You get `https://<name>.vercel.app`.

## 3. Connect them

In Render, set `CORS_ORIGINS` and `FRONTEND_URL` of **both** services to your Vercel URL
(several are allowed, comma-separated, e.g. `https://timetabl-ai.vercel.app,http://localhost:3000`).
Render redeploys by itself.

## 4. Check the live site

1. Open the Vercel URL → one-click **College Admin** demo login (password `demo1234`).
2. Dashboard shows 0 clashes and a quality score; **Timetable** opens; drag a class → review → Apply → Undo.
3. Log in as the Student demo → only CSE-3A's classes; press **Ctrl+K** and ask "What do I have tomorrow?".

## Plans and speed

- **Free plan**: the service sleeps after 15 minutes without visitors; the first visit after that waits
  ~1 minute. It also has a tenth of a CPU, so generating a timetable is slower and the quality lower.
- **Starter plan** (`plan: starter` in `render.yaml`): always on, half a CPU, 512 MB. Fine for the demo.
  Generating the demo college peaks at ~280 MB.
- Open the site 5 minutes before presenting, whichever plan you use.

## Rules that keep it correct

- Keep **one process** per service (`--workers 1`). Data is kept in memory and saved to Supabase in
  the background, in order; two processes would not see each other's changes.
- Never commit `.env` files. Change a secret in the dashboard, not in code.
